# A Key Value Cache for Exact Attention over Subsets

Release repository for the paper of that title. It holds the library source at the versions measured, the five notebooks that produced the paper's measurements and generated tables, the saved result files, the 18 benchmark inputs, the four pilot data extracts, a manifest of file hashes and the license. This README gives the full benchmark protocol, every table not printed in the paper, the counting checks, the pilot details and the four reproduction routes that Section 6.6 of the paper names.

Repository: https://github.com/jakemdrew/subset_cache_pub
Release tag: talg-submission.

Measured code and release commit. The code that produced every measurement is identified by the SHA256 of each library module, recorded in both benchmark result files and in the pilot gate record, and checked again by the manifest notebook. The release commit also carries documentation, caption and generator text changes made after the measurements. It therefore need not be the commit at measurement time. Agreement of the module hashes, not identity of commits, ties the released code to the reported results.

## Benchmark protocol

Machines. The 2080 has an RTX 2080 SUPER GPU with 8 GB of memory and runs Windows with PyTorch 2.5.1. The H100 has an H100 GPU with 80 GB of memory and runs Linux with PyTorch 2.8.0. The H100 is a rented cloud instance, a container on a shared server with an Intel Xeon Platinum 8470, whose scheduler quota limits the container's CPU time to the equivalent of 22.1 cores. TF32 is disabled on both machines. Both run the same library code, verified by hash. Differences between their results combine differences in GPU, CPU, operating system and software.

Inputs. The suite has 18 inputs, and each machine runs all of them, giving 36 benchmarks. An input is generated once from a fixed seed, so both machines receive the same subsets and tensors. The actual number of subsets P, at most M, is recorded with each input.

Attention benchmarks. An attention benchmark times the forward and backward passes of the loss sum(W * out), for fixed random weights W. It uses seeded random query, K and V in float32, with C = 24 channels and d_k = d_v = 80. The main comparison uses the run sampler at n = 300 and 496, with requested budgets M = 64,000, 128,000, 256,000 and 512,000. The small record boundary uses the full power set at n = 14 and 16, so P = T. The fixed size run sampler and the individual sampler run at n = 300 and 496 with M = 64,000. Every run sampler input uses the requested run length lambda = 10n.

Training step benchmarks. A training step benchmark times one complete training step on a real record with 300 or 496 features. It includes the encoder, the keys and values, predictions from all features together and from the sampled subsets, the loss, the backward pass and the AdamW update. It uses the run sampler at M = 64,000 and 512,000, with lambda = 10n. A pretrained bidirectional set encoder runs once over the record. The keys and values each encoder block computes for each feature are recorded and reused by every subset. Learned channel queries, one per layer and head, score the keys. Every method runs from restored model, optimizer and random number generator states.

Cache. The cache uses the level walk with the closed form backward pass. It first runs unchunked over all P subsets. If that call runs out of memory, it runs again over g = 2, 3, ..., 8 groups and keeps the first g that fits. A group is a contiguous range of the sorted subsets with its own trie and level plan. The g - 1 cuts start at the equal splits of P. Each cut then moves, within 1 percent of P on either side, to the boundary where the two neighboring subsets share the fewest prefix features. On run sampler and full power set inputs the cache's trie is generated from the run descriptor, the first rank and the length of each run, by the successor rule of Section 5.6, and no subset list is read. Group tries are generated the same way from the intervals each group covers. On fixed size run and individual sampler inputs the trie is built from the subset list. Cache replay captures the unchunked cache call once as a CUDA graph, after three graph warmups, and each timed call replays it. Cache replay has no grouped fallback.

Direct methods and backend@chunk. A direct combination is one direct method with one backend at one chunk size. Masked attention with the default backend, masked attention with the mathematical backend and gathered attention each run unchunked and at chunk sizes 4,096 and 1,024, giving nine eager direct combinations. A masked attention combination is written backend@chunk, with default or math as the backend and all for unchunked, so math@4096 is masked attention with the mathematical backend at chunk size 4,096 and default@all is masked attention with the default backend unchunked. The table key letters are a, b and c for math@all, math@4096 and math@1024, d, e and f for default@all, default@4096 and default@1024, and g, h and i for gathered attention unchunked, at 4,096 and at 1,024. A masked attention replay captures one masked attention combination as a CUDA graph and replays it, giving six masked attention replays. Its whole P x n mask is moved to the GPU once before capture. Gathered attention builds its indices on the host inside each call, so it has no replay. Cache replay is therefore compared with the replay of masked attention, which was the fastest eager direct method in every main benchmark.

Comparison. The eager cache is compared with the fastest timed of the nine eager direct combinations. Cache replay is compared with the fastest timed of the six masked attention replays. The speedup is that direct median divided by the cache median, so a speedup above 1 means the cache is faster. A method that runs out of memory is not a candidate.

Ceiling. Each method first runs once exactly as it is timed. If that call takes longer than 30 s, the method is not timed further. The two exclusions are in tab_ceiling.

Replay verification. Cache replay and the masked attention replays are the replay methods. Before any timed call, the captured graph of each replay method is replayed three times untimed, and each later execution is compared with the first. For a training step, the first execution is also compared with the eager step of the same method from the same starting state, over the loss, the gradients, the parameter update, both AdamW moment buffers and the step counters. A replay method that fails is not timed.

Timing. Each method runs two untimed warmups and five timed repeats. A repeat is the synchronized wall clock of one call. Every repeat is saved, and the median is reported. An eager direct call includes the transfer of each mask chunk to the GPU. A training step starts from a restored state and ends after the optimizer update.

Memory. Memory is the peak GPU memory during one call, with the counters reset before each call. For eager methods it is the memory allocated. A replay keeps its intermediate tensors in the graph's memory pool, so for replay methods it is the memory reserved. The two measures are not directly comparable.

Preparation. Preparation is the work done before a timed call. Four components are timed, each the median of five repeats.

| Component | Definition | Needed by |
|---|---|---|
| Input generation | regenerates query, K, V and W from the seed on attention benchmarks. It is the benchmark's synthetic input, the same work for every method, reported once and excluded from the comparison of methods | every method, excluded |
| Subset materialization | regenerates the subset list from the sampler's key | masked and gathered attention, and the cache on fixed size run and individual sampler inputs |
| Cache own preparation | the trie, the level plan and the plan's transfer to the GPU. On run sampler and full power set inputs it includes the reconstruction of the rank intervals from the run descriptor | the cache |
| Masked attention own preparation | the P x n mask on the CPU, whose transfer is counted in eager execution | masked attention |

A method's method preparation is the sum of the component medians it needs. For a grouped cache, method preparation is a single timing of the interval reconstruction and the construction and transfer of all group plans. Method preparation plus execution adds the eager execution median. Both are sums of medians, not one clock. The single clock times a method's fresh preparation and one eager execution together, after runtime warmup, with every prepared object discarded before each repeat. It covers eager methods only and does not measure process first use. Graph warmups, capture and the replay mask transfer are timed once per replay method and reported separately in tab_replay_setup.

## Numerical agreement

The reference combination is masked attention with the mathematical backend at chunk size 1,024. It runs first in each benchmark, and its outputs and gradients must be finite. Every other method is compared with it in float32 on the same GPU.

Attention. Each comparison covers the attention outputs and the gradients of the attention benchmark loss with respect to query, K and V. Let Delta be the difference from a reference tensor ref, and ||.|| the Euclidean norm of a flattened tensor. Each output must satisfy max_j |Delta_j| <= 1e-6 + 1e-4 max_j |ref_j|. Each gradient must satisfy ||Delta|| / ||ref|| <= 1e-3, or ||Delta|| <= 1e-6 against a zero reference.

Training step. The same parameters must receive gradients, the loss must agree within 1e-6 + 1e-4 |ref|, and the flattened gradient of all parameters must satisfy ||Delta|| / ||ref|| <= 1e-3.

Result. Each benchmark has 16 agreement checks, one for every method except the reference combination, so there are 576 checks over both machines. 466 ran and passed, and none failed. The other 110 did not run.

Scope. Agreement within tolerance holds only for these methods and inputs, in float32 and for first order gradients on the GPUs of the two machines. The benchmark comparisons were not run in half precision or float64, and second order gradients were not checked. Tied scores were not tested separately, and Section 4.5 of the paper gives the argument for them. Parameters and optimizer state after the update of a training step were compared only between each replay method and its eager step, not with the reference combination.

## Pilot settings

Transcribed from masked_concept_model.py, mc_batched.py and the pilot notebook's Cells 2 and 5. In the notebook the baseline and the subset supervised model are the runs W0 and W, and the baseline under the registered rule is W0_registered.

Notation. A stored value v is a percentage change expressed as a fraction (0.25 for 25 percent), and g(v) = sign(v) log(1 + |v|). For a context, either all of the record's other features or a subset of them, c denotes the number of features it contains.

Model. d = 256, H = 4 heads of 64, two encoder blocks, prediction head width 256, Huber delta = 1, 1,647,627 parameters, counted by Cell 10 over the 35 floating point tensors of the saved model state.

- Feature encoder, applied to each feature on its own. The feature's 384 dimensional concept name vector passes through a bias free linear adapter to d. The term g(v) w_val + b_val is added. Two residual blocks follow, each LayerNorm, linear d to 4d, GELU, linear 4d to d. A final LayerNorm comes next, and then linear key and value projections d to d, split into H heads.
- Concept query. The target concept's name vector passes through its own adapter, a learned mask vector is added, and then LayerNorm and a linear projection d to d split into H heads.
- Score z = k^T q / sqrt(64) per head, with k the feature's key.
- Prediction head. Its input is the output vector of each head (H by 64), the per head log normalizer m + log s (H), log(1 + c), and the concept query embedding (d). It applies LayerNorm, linear to 256, GELU, linear 256 to 256, GELU, linear to 1. For a subset, c is formed from the terminal's depth in the trie.

Construction is seeded with 367 and is deterministic.

Optimization.

- AdamW with learning rate 3e-4, weight decay 0.01, betas (0.9, 0.999), eps 1e-8, float32, no gradient clipping. A nonfinite gradient stops the run before the update.
- Per target losses are accumulated over successive microbatches. One update is taken at 32 or more targets, or at the end of the epoch, with gradients divided by the accumulated target count.
- The learning rate is set by cumulative target exposure t, evaluated at the end of each accumulation group. With eta = 3e-4, t_w = 123,490.2 (10 percent of one epoch's 1,234,902 targets) and t_T = 9,879,216 (8 epochs), eta(t) = eta t / t_w for t < t_w, and eta/2 (1 + cos(pi min(t - t_w, t_T - t_w) / (t_T - t_w))) for t at or above t_w. Two of the 8 epochs were run, and the rate at the end of epoch 2 is 2.59e-4.
- Microbatch order within an epoch is a permutation seeded by (367, epoch, 131), and every training occurrence is a target exactly once per epoch.
- Under the accumulated rule, the subset supervised model and the baseline each take 32,995 updates in epoch 1 and 32,958 in epoch 2. The baseline under the registered rule takes one update per microbatch.

Objectives and masking.

- The baseline uses the context term alone. The context is the whole record with the target removed.
- The subset supervised model adds a subset term over subsets of the record's features drawn by the run sampler, with requested budget M = 2,048 and run length lambda = n, keyed by the record name and the epoch. Each target's trie is built from the drawn subsets that exclude the target, so an unusable subset never enters the trie. The usable subset losses are summed and divided by the Horvitz Thompson denominator P (2^(n-1) - 1) / (2^n - 1), computed in float64 as P (1 - 2^-(n-1)) / (2 - 2^-(n-1)) without forming 2^n.
- The per target loss of the subset supervised model is 0.5 times the context term plus 0.5 times the subset term. A target with no usable subset contributes only the 0.5 weighted context term.
- The run sampler delivered a mean of 1,968 subsets per record, with a minimum of 3, against the requested 2,048. In expectation 2^(n-1) / (2^n - 1) of them, just over half, contain a given target and are unusable for it. For about 5.6 percent of sampled targets no drawn subset was usable in the microbatch.
- The data loader constructs each microbatch's items, the subset draw and one trie per target built from it, outside the timed execution of the cost study. The run trie generator is not used for these per target tries.

Evaluation.

- Every held out feature is a target. Each held out prediction uses all other features of the record as its context, with the target excluded, for the baseline and the subset supervised model alike. No sampled subset enters evaluation.
- Losses are Huber in signed log space, per target.
- Intervals, 2,000 resamples of held out records with replacement, seed (367, 91). Each interval is the 2.5 and 97.5 percentiles of the resampled mean of the paired per target differences.
- Context permutation probe. 20 held out records with at most 1,024 features, chosen with seed (367, 181). Every feature of each probed record is a target. Target identities, concept names and context membership stay fixed. The features' values are reassigned across the record's positions by one permutation per record, with seed (367, 171, record). Because the permutation is record wide, a target's own original value can move to another position inside its context. The probe value is the median absolute change in prediction, pooled over all probed targets of all 20 records. It compares predictions only and uses no labels.

## Determinism and artifact scope

Model construction is deterministic from the seed, and its initialization hash is asserted before every pilot run. Microbatch plans are deterministic from the seed and epoch, and their hashes are asserted. Every sampler is a deterministic function of recorded identifiers. Every contract is recomputed and matched before a run proceeds. These controls fix the initialization, the data order and the sampled subsets. They do not make GPU training bitwise deterministic, which would require deterministic execution to be enabled and verified, and this was not done. Determinism across hardware or library versions is not guaranteed. Results are therefore tied to the recorded environment, and agreement is stated within tolerance rather than as identity.

The notebooks regenerate every generated table, the two generated figures and every interval from the saved results. The benchmark tables, the two figures and the counting checks need no GPU. The pilot intervals and tables need a CUDA device, because the pilot notebook's Cell 2 asserts one. Rerunning the benchmarks requires a compatible GPU. Pilot training runs from the supplied data extracts. The counting theorems are independent of these empirical limits, provided their assumptions hold.

## Data availability

The pilot data extracts are supplied, so the pilot retrains from this repository. Regenerating the extracts, or the four training step benchmark inputs, requires the source data store, which is not supplied. The 14 attention benchmark inputs regenerate from recorded seeds.
